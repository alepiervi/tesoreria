# RCA — Bank balances sent "in rosso" after "Annulla import" (DELETE /api/statement-imports/{id})

App: gestione-tesoreria-1 (Nureal-Amministrazione) · FastAPI + MongoDB · DB `gestione-tesoreria-1-tesoreria`
Active run: 40b39f07-bbe4-44d8-b529-8600811929bf
Report (IT): dopo aver cancellato gli estratti caricati, i conti sono andati "completamente in Rosso".

## Verdict
Confirmed. The user's suspected cause is correct. The undo path, for **legacy import records that predate the `balance_before_cents` field**, recomputes the balance as `balance_cents − Σ(deleted transactions)`. Those legacy imports had SET the balance from the statement's closing figure (not base+sum), so subtracting the movements is arithmetically wrong and drove the account strongly negative. This is a **source/logic bug (Code)**, not infra, secrets, or a bad deploy.

## Root cause (source), `backend/app/routers/banks.py`

Import (writes balance; current build adds balance_before/after — line ~451+):
```
elif plan["mode"] == "file":
    balance, balance_date = plan["base_cents"], ...   # balance SET to statement closing balance
...
"balance_before_cents": account.get("balance_cents", 0), "balance_after_cents": balance,  # new builds only
```
Undo (`undo_import`, line ~498):
```
if "balance_before_cents" in record and is_last:
    balance = record["balance_before_cents"], ...            # correct path (new records)
else:
    balance = account.get("balance_cents", 0) - sum(t["amount_cents"] for t in txs)   # <-- BUG for legacy
```
Because the two records are legacy (`balance_before_cents` absent), undo took the `else` branch and did `balance − Σ(movimenti)`. That is only valid if the import had done base+Σ. These imports instead SET the balance to the file's closing figure, so subtracting the movements double-removes them → -€1.106.633,98.

Contributing factors:
- `_import_transactions` legacy fallback (line ~466) re-identifies "which movements belonged to this import" by a fragile heuristic (source="import", no import_id, date within [date_from,date_to], created within 5 min of the import `at`). Any mismatch skews the subtracted sum further.
- Undo order: the first undo (older PDF import) ran while the newer CSV import was still active, so `is_last` was False — even a non-legacy record would not have restored `balance_before_cents` in that order.

## Recoverability
The exact correct balance is **NOT deterministically recoverable from the production DB**:
- The 96 imported transactions were hard-deleted; there is no soft-delete/trash collection and no copy in `outbox` (2 unrelated docs from 11-09 and 11-16).
- The opening balance entered at account creation was overwritten in `bank_accounts.balance_cents` and was never captured in the audit `details` ({}).
- `backup.py` writes `.json.gz` to the pod filesystem (BACKUP_DIR), not into Mongo — ephemeral, not available here.

## Suggested repair
1. User supplies the correct figure (only they have it): either the opening balance they typed at account creation, or the closing balance shown just before they clicked "Annulla". Then rebuild the account — preferred: re-import the two original files ("Estratto conto corrente_30-09-2026.pdf" and "10.2026.csv") on the current build (which now stores balance_before/after and will compute correctly), OR set `bank_accounts.balance_cents` for id `3c7a009f-2413-4b7d-9811-7c2d04ff2175` to the correct value via the DB manager.
2. Code fix (E1): in `undo_import`, when `balance_before_cents` is absent (legacy record) never do `balance − Σ(txns)`. Instead refuse the undo and ask the user to set the balance manually, or restore from a reliably reconstructed base; also harden `_import_transactions` and handle undo order so an older import can't be undone with a wrong anchor while a newer one is active.

Note: code path verified by reading source in an eph sandbox; the data-level consequence verified directly against the production DB. The bug was not re-executed live (would require the live DB + real files).
